# 08. Documentation & Code Comments Specification

This specification follows official Go documentation standards ([Effective Go - Commentary](https://go.dev/doc/effective_go#commentary), [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments#comment-sentences), [Go Doc Comments](https://go.dev/doc/comment)), clarifying the required depth, syntax, and structure of Go comments generated by LLMs.

---

## 1. Core Comment Principles

1. **100% Exported Identifier Comment Coverage**:
   - Every exported **package, struct, interface, function, method, constant, and variable** must have a formal GoDoc comment.
2. **Sentences Starting with Identifier Name**:
   - Doc comments must be **complete sentences** and **must start with the identifier's name** (even if it feels slightly repetitive, this is the official GoDoc standard).
3. **Usage Examples Required for Critical/Core Functions**:
   - For core business use cases, low-level algorithms, or public SDK/API methods, comments must provide representative usage code examples or companion `ExampleXxx` test functions.
4. **Explain "Why", Not Just "What" in Code Blocks**:
   - Line-level comments inside code blocks **must never redundantly narrate what the code does** (e.g., `// increment i`). Instead, explain the **design intent, business background, concurrency synchronization rationale, defensive boundary invariants, or trade-offs**.

---

## 2. GoDoc Commentary Standards for Exported Identifiers

### 2.1 Package Comments
Every package must include an introductory doc comment preceding the `package` clause. Multi-file packages typically concentrate the package comment in a dedicated `doc.go` or in the primary entrypoint file:

```go
// Package auth provides JWT and secure cookie authentication, session management,
// and RBAC authorization middleware.
//
// The package follows OWASP security standards; all session cookies are protected
// with HttpOnly and SameSite attributes by default.
package auth
```

### 2.2 Struct & Interface Comments
```go
// OrderManager orchestrates the complete lifecycle of orders, including creation,
// payment state transitions, and inventory deduction.
// OrderManager is safe for concurrent use by multiple goroutines.
type OrderManager struct {
	repo   OrderRepository
	logger *slog.Logger
}

// PaymentGateway defines the contract for interacting with external payment providers (e.g., Stripe, PayPal).
// All implementations must ensure idempotency and honor context cancellation.
type PaymentGateway interface {
	// Pay initiates a single payment charge.
	// If the charge was previously processed, it must return the existing transaction
	// details rather than duplicating the debit.
	Pay(ctx context.Context, req *PaymentRequest) (*PaymentResult, error)
}
```

### 2.3 Exported Function & Method Comments
```go
// CalculateTax calculates applicable taxes based on the customer's jurisdiction and line items.
// If the jurisdiction has no custom tax rule configured, it falls back to the statutory base rate.
func (m *OrderManager) CalculateTax(region string, items []Item) (decimal.Decimal, error) {
    ...
}
```

## 3. Usage Examples for Critical Functions

For core business functions, generic libraries, and non-trivial APIs, doc comments must supply an indented code block illustrating typical usage:

### Standard Example
```go
// BatchRetry executes the given closure with exponential backoff according to the supplied RetryPolicy.
//
// When the closure returns a non-recoverable error (e.g., ValidationError), BatchRetry aborts immediately
// and returns the root error. If the closure succeeds within the retry budget, or exhausts max attempts,
// the final result is returned.
//
// Example usage:
//
//	policy := RetryPolicy{
//	    MaxAttempts: 3,
//	    InitialBackoff: 100 * time.Millisecond,
//	}
//	err := BatchRetry(ctx, policy, func(ctx context.Context) error {
//	    return client.SyncData(ctx)
//	})
//	if err != nil {
//	    slog.Error("batch retry failed", "err", err)
//	}
func BatchRetry(ctx context.Context, policy RetryPolicy, fn func(ctx context.Context) error) error {
    ...
}
```

> [!TIP]
> **Executable Test Examples**: For shared libraries in `pkg/`, write `func ExampleBatchRetry()` in a `_test.go` file. GoDoc automatically extracts and renders it as an interactive, runnable documentation example.

## 4. In-Block Comments: Explain "Why", Not Just "What"

Inside function bodies, quality comments explain **constraints, architectural trade-offs, non-obvious logic, and defensive assumptions**:

### ❌ Anti-Pattern: Redundant Syntax Narration
```go
// Acquire lock
mu.Lock()
// Release lock
defer mu.Unlock()

// Return error if users is empty
if len(users) == 0 {
    return errors.New("empty users")
}

// Loop through users slice
for _, u := range users {
    // Log user ID
    slog.Info("processing", "user", u.ID)
}
```

### ✅ Best Practice: Explaining Intent & Invariants
```go
// Acquire read lock prior to snapshotting state to prevent a data race with the background refresh worker.
mu.RLock()
snapshot := make([]TargetNode, len(nodes))
copy(snapshot, nodes)
mu.RUnlock()

// Invariant assertion: An empty batch must never be dispatched to the bulk database engine,
// as the underlying SQL driver rejects empty VALUES statements with an unhelpful syntax error.
if len(users) == 0 {
    return apperrors.NewInvalidArg("users slice cannot be empty")
}

// Note: A buffered channel (size = 100) is chosen instead of an unbuffered channel
// to absorb brief webhook bursts without blocking inbound HTTP handlers during downstream GC pauses.
taskQueue := make(chan Task, 100)

// Defensive delay: Workaround for early Linux/macOS kernel socket reuse quirks;
// brief 5ms pause ensures underlying TCP handles cleanly detach from TIME_WAIT before rebinding.
time.Sleep(5 * time.Millisecond)
```

## 5. Standard Directives & Annotations

When code deprecations, temporary compromises, or known limitations exist, use standard annotations:

### 5.1 Deprecation (`Deprecated:`)
Go linters and IDEs parse comments starting with `// Deprecated:`. Always identify the recommended replacement:
```go
// QueryUserByID retrieves basic profile information for a user.
//
// Deprecated: QueryUserByID does not support multi-tenant isolation.
// Migrate to [QueryUserByIDWithTenant] which supports tenant scoping and context propagation.
func QueryUserByID(id string) (*User, error) {
    ...
}
```

### 5.2 Tasks & Known Limitations (`TODO` & `BUG`)
- Format: `// TODO(<owner/issue>): <concrete actionable resolution>`
- Never leave anonymous, unassigned `// TODO` comments.
```go
// TODO(developer): Replace in-memory token bucket with Redis sliding window limiter once distributed cluster is ready (Issue #142)
if !limiter.Allow() {
    return ErrRateLimited
}

// BUG(developer): On Windows platforms, paths containing non-ASCII characters may be truncated by the legacy syscall.
```

---

## 6. Comments Self-Checklist

Before finalizing and delivering code, check:
- [ ] Every exported package, struct, interface, function, and constant has a GoDoc comment whose first sentence starts with the identifier's name.
- [ ] Core business methods and complex utility functions include clear parameter and usage examples.
- [ ] Concurrency synchronization (channels, mutexes, goroutines) and non-obvious branching explain "why".
- [ ] Deprecated APIs use standard `// Deprecated:` annotations pointing to modern replacements.
- [ ] No meaningless comments that merely rephrase syntax.
